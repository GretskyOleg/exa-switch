# Безопасность EXA Switch

Документ описывает модель угроз, результаты аудита и остаточные риски.
Аудит проводился по коду расширения, helper'а и схеме установки (пакет/signed XPI).

## Модель угроз

| Субъект | Что может | Что защищает |
|---|---|---|
| Внешний сайт | отправить запрос на `127.0.0.1:<helper>` | `Host`-guard, CORS, Bearer-токен, случайный порт |
| Вредоносная подписка / VLESS-ссылка | подсунуть огромный ответ, странные поля, инъекцию в xray-конфиг | лимиты размера, валидация полей, allowlist транспортов/протоколов |
| Другое расширение браузера | обратиться к helper'у, прочитать storage | CORS только для ID нашего расширения (Chrome), токен, изоляция storage |
| Другой процесс того же пользователя | прочитать `daemon.json`, подключиться к SOCKS/HTTP | `0600`/`0700`, loopback, fail-closed; см. остаточные риски |
| Вредоносный экспорт настроек | подменить профиль/outbound | профиль пересобирается из `vless://`, helper принимает только VLESS |
| Компрометация обновления | подменить XPI | подпись Mozilla (AMO), установка только подписанного файла |

## Что было найдено и исправлено

### 1. Неограниченное чтение подписки (DoS) — исправлено

`fetchSubscription` читал весь ответ `res.text()` и только потом проверял размер.
Вредоносный сервер мог отдать гигабайты и подвесить service worker/вкладку.

**Исправление:** чтение потоком с жёстким лимитом 2 МБ, проверка `Content-Length`,
отмена чтения при превышении, запрет редиректов (`redirect: "error"`), лимит длины URL.

### 2. Инъекция произвольного outbound в xray-core — исправлено

`importSettings` принимал профили как есть, а helper запускал `outbound` из
`/api/start` без проверки протокола. Импортированный JSON (или подменённое
хранилище) мог заставить xray-core запустить `freedom`, `blackhole`,
`dokodemo-door` и т.п.

**Исправление (два уровня):**

- расширение при импорте и перед каждым стартом **пересобирает профиль из
  `vless://`-ссылки** (`sanitizeProfile` / `outboundForProfile`);
- helper валидирует outbound (`validateOutbound`): только `protocol=vless`,
  ровно один `vnext`, один пользователь, допустимые `network`/`security`,
  лимит 256 КБ, запрет лишних полей. Всё остальное → HTTP 400.

Добавлен регрессионный тест: helper отклоняет `freedom`, `dokodemo-door` и
пустой `vnext`.

### 3. Инъекция полей VLESS-ссылки — исправлено

Поля `path`, `host`, `sni`, `pbk`, `sid`, `spx`, `serviceName`, `authority`,
`extra` и др. попадали в JSON без ограничений. `extra` мержился в
`xhttpSettings` как произвольный вложенный объект.

**Исправление:** лимиты длины, запрет управляющих символов, проверка charset
для UUID/адреса, `extra` — только плоский объект (до 20 ключей, примитивы,
строки ≤ 256 символов), числовые параметры KCP зажаты в разумные диапазоны,
сама ссылка ограничена 8 КБ.

### 4. CORS принимал любое расширение — исправлено

Раньше helper разрешал `Origin: chrome-extension://*` и `moz-extension://*`.

**Исправление:** для Chrome разрешён только точный ID
`bdbbepgnedpgfieoimcbbbigkkkcfhpl`; для Firefox — `moz-extension://` (UUID
генерируется браузером и неизвестен на этапе сборки) плюс обязательный
Bearer-токен. Добавлены `X-Content-Type-Options: nosniff` и `Referrer-Policy`.

### 5. Границы ввода API — исправлено

`/api/health` принимал URL любой длины, `/api/start` — `id`/`name` любой длины,
HTTP-сервер не ограничивал заголовки.

**Исправление:** лимиты на target (2048), `id`/`name`, `MaxHeaderBytes`,
`IdleTimeout`, лимит логов уже был. В расширении — проверка схемы `http(s)`,
лимит `limit` для логов.

### 6. Защита от сообщений «не от нас» — добавлено

В `runtime.onMessage` добавлена проверка `sender.id === runtime.id`
(защита в глубину; `onMessageExternal` не регистрируется).

### 7. Ужесточение службы — добавлено

`xray-switch.service`:

```
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=full
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true
RestrictSUIDSGID=true
RestrictRealtime=true
LockPersonality=true
UMask=0077
```

Служба работает от пользователя, не от root.

### 8. Установка только подписанного расширения — сделано

Пакет кладёт в Firefox **подписанный Mozilla** XPI (AMO, unlisted).
Неподписанные сборки в release-Firefox не устанавливаются. CSP расширения —
`script-src 'self'; object-src 'self'`, внешних скриптов нет, `eval`/`innerHTML`
не используются. В пакете дополнительно включена политика
`Extensions.Install` + `Extensions.Locked`, чтобы расширение ставилось
автоматически и не могло быть случайно удалено или отключено из `about:addons`;
при удалении пакета `post_remove` убирает и policy-запись.

Для Chrome/Chromium/Edge/Brave/Vivaldi собирается подписанный **CRX3**.
Приватный ключ лежит в `packaging/.keys/chrome.pem` и **не должен попадать в
git** (каталог в `.gitignore`). Он нужен для обновлений с тем же Chrome ID;
если ключ потерян, генерируется новый, но меняется ID и его надо обновить в
`extension/manifest.chrome.json`, `helper/api.go`, `packaging/installer/main.go`.
Публичный ключ хранится в манифесте, по нему вычисляется ID.

## Остаточные риски (честно)

1. **SOCKS/HTTP helper'а без пароля.** Любой процесс вашего пользователя может
   найти порт (или прочитать `daemon.json`) и использовать туннель. Это
   архитектурное ограничение: PAC и `proxy.onRequest` не умеют авторизацию в
   SOCKS. На многопользовательской машине используйте отдельного пользователя.
2. **Токен в `daemon.json`.** Файл `0600`, каталог `0700`, но процесс того же
   пользователя может его прочитать. 256-битный токен защищает от внешних
   сайтов и других расширений, но не от локального кода с вашими правами.
3. **Гонка портов.** `freePorts` освобождает порты перед стартом xray-core;
   локальный атакующий теоретически может занять порт первым. Helper
   перевыбирает порт при `address already in use`, а расширение работает
   fail-closed. Полное устранение потребует передачи уже открытых сокетов в
   xray-core.
4. **Обновления расширения.** Unlisted-сборка не обновляется автоматически;
   новая версия приходит с новым пакетом. Следите за версией.
5. **xray-core.** Это большой сторонний код (MPL-2.0). Обновляйте helper вместе
   с xray-core; смотрите `THIRD_PARTY.md`.
6. **Firefox host permission `<all_urls>`.** Нужен для `proxy.onRequest`, чтобы
   видеть URL запросов. Content scripts не внедряются, данные никуда не уходят.
7. **DNS VLESS-сервера** резолвится системным DNS. Целевые домены уходят на
   сервер (SOCKS с `proxyDNS: true` в Firefox; Chrome отправляет hostname в
   SOCKS5/HTTP). Если системный DNS подменён, адрес сервера тоже может быть
   подменён — используйте доверенный DNS/DoH на уровне ОС.
8. **Компрометация пользователя.** Если вредоносный код уже работает с вашими
   правами, он может пользоваться туннелем и читать конфиг. Это вне модели
   угроз браузерного расширения.

## Что не делает расширение

- не отправляет профили, UUID и правила на сторонние серверы;
- не содержит аналитики/телеметрии (`data_collection_permissions: none`);
- не внедряет content scripts в страницы;
- не запрашивает доступ к сайтам, пока вы не импортируете подписку;
- не запускает произвольные бинарники: только зарегистрированный native host.

## Как сообщить о проблеме

Не публикуйте UUID, VLESS-ссылки и `daemon.json`. Для отчёта достаточно:

- версия (`xray-switch-helper version`, версия расширения);
- ОС и браузер;
- шаги воспроизведения;
- фрагмент `journalctl --user -u xray-switch` **без** токена и ссылок.

## Проверки

```bash
./tests/run.sh          # Node 20+, helper собран
node --test tests/helper-smoke.mjs
```

Тесты покрывают: парсинг ссылок, PAC, правила, импорт/экспорт, подписки,
fail-closed, запуск всех транспортов и **отказ helper'а от не-VLESS outbound'ов**.
